## 刷新为何显得不自然

两个入口都调用 `DesktopCanvas::refreshAll()`。旧流程在每次刷新时删除、重建全部普通散落图标，清掉其选中状态；即使文件没有变化，也触发全部图标的白色闪烁动画和同步整桌面绘制。异步壁纸读取完成后，无条件清除壁纸和分区玻璃缓存。分区内部图标只闪烁，同路径 `.desktop` 的名称、图标等元信息却没有重新读取。

独立 Xvfb、D-Bus、XDG 目录中的真实右键菜单回归，在修改前复现三个失败：原控件被销毁、选中状态丢失、未变化的壁纸发出重新构建通知。无需改变桌面文件也能复现。

更合理的职责是：同步外部变化、刷新文件元信息，并修复失效监听；刷新本身不充当视觉动画或重新排列命令。

本轮实现：

- 保留未删除文件的 `DesktopIcon`，在原控件上更新散落及分区图标的元信息。保留选中状态及有效手动位置，只有真实新增/删除才改变文件集合；自动排列仍按用户原有设置执行。
- 移除刷新专用白色闪烁动画，使用 Qt 合并绘制请求。文件夹预览信息仍在手动刷新时失效，避免沿用旧内容。
- 对比解码后的壁纸像素、实际绘制模式及来源状态。无变化时保留材质缓存；同路径图片替换、绘制模式变化仍重新构建。
- 保留桌面目录/回收站监听重绑、丢失图标显示恢复，以及 450/1400 毫秒后续扫描，兼容文件临时写入后改名的保存方式。
- 菜单名称保留「刷新桌面」，提示说明同步文件、图标和壁纸并保留位置、选中状态。桌面菜单打开时原有的分区选择清理规则不属于刷新逻辑；F5 本身保留分区选择。

回归通过实际右键 QAction 与 F5 检查控件身份、选择、位置、图像、同路径元信息更新、外部新增/删除、桌面目录替换后继续自动监听，以及同路径壁纸更新。采用 100%、150%、200% 三档缩放。

限制：手动刷新仍在 GUI 线程读取文件元信息，大型桌面尚未测得需要搬到后台的依据；没有把刷新扩展成应用重启或强制重新排列。后续扫描仍按原有逻辑执行，不表示长期索引。

### 补测发现的真实撤回缺陷

同一路径两次删除，如果中间文件由外部程序重新创建，旧 `pushUndo()` 仅按类型、源/目标路径及分区去重，会把第二次删除当成重复信号丢掉。已有准确回收站实体记录因此无法正常按代次撤回。

新增 Canvas 级回归先复现失败，再将去重条件补上完整 `TrashEntry` 对应表。相同回执仍去重，不同代次依次保存。测试按 Ctrl+Z 确认先恢复第二代，再用唯一名称恢复第一代，实际读取两份内容并确认不覆盖。

## 批量删除对比

同机、相同 fixture：回收站预置 5000 条旧 trashinfo，一批删除 200 个文件，使用真实 GIO、独立 HOME/XDG 数据目录。

| 实现 | 耗时 | 准确回执 |
| --- | ---: | ---: |
| 原逐文件全量扫描 | 18,682 ms | 200/200 |
| 按批基线与增量核对 | 2,366 ms | 200/200 |

单次对比约减少 87% 耗时，不能当作统计性能承诺。没有个人回收站数据参与。故障注入另覆盖 inotify 不可用及丢弃事件后注入 `IN_Q_OVERFLOW`；两者都必须仍通过完整撤回回归。

inotify 溢出后的完整协调遵循 [Linux inotify 文档](https://man7.org/linux/man-pages/man7/inotify.7.html)。原有跨文件系统 OEM GIO 拒绝情况仍保留在上一轮文档中，未取得实际 U 盘正向恢复证据。

# 刷新反馈与启动首屏修复（2026-10-01）

基线：`6cfefe489f0aaf36dd07ae7c4357204d201fb6f7`。用户确认手动刷新需要短闪反馈，并反馈进入 Fences 时先出现蓝色分区、约五秒后才恢复材质及小组件。

## 当前行为

- 右键「刷新桌面」和 F5 在现有散落及分区图标上播放一次约 180 ms 的白色淡入淡出。重复刷新重启同一个动画，不叠加定时器；不隐藏、删除或重建未变化图标，保留选择和有效位置。
- 壁纸解码后，在后台准备分区材质；完成后在隐藏画布上缓存真实分区表面，包括首次 GPU 编译。恢复已启用的时钟、活动、音乐、日历和系统监视，再显示画布。未开启液态玻璃或没有分区时无需等待这项准备。
- 缺失或解码失败的壁纸使用原有渐变准备材质，仍释放启动门控；启动过程中用户隐藏桌面的操作继续有效。
- 智能空间在组件构造后后台读取现有索引、解压 gzip、解析 JSON 和续扫状态。界面显示“正在加载本地索引…”，不因打开而扫描文件。完成后在界面线程发布条目、显示首批卡片和恢复监听。
- 后台任务只捕获路径、参数和图像等值，组件销毁后丢弃回调。索引的新发布会淘汰旧读取结果；排除范围按交付时的当前设置处理，加载期间新增排除或恢复范围都生效。加载结果不覆盖进行中的索引任务状态文案。
- 液态小组件共用一个 GUI 线程中的 GPU 上下文、着色器程序和输出 FBO，避免每个小组件重复编译。各渲染器独立保留输入图像、形状和外观参数，每次渲染重新设置参数；弱引用共享，不在最后一个渲染器销毁后保留 GL 资源。GPU 不可用仍走原有 CPU 降级。

## 原因与测量

原分区材质在 `paintEvent()` 中首次触发后台准备，因此画布已经显示时会先采用蓝色备用样式。原智能空间构造函数还在 GUI 线程读取全部索引。当前机器缓存主索引约 151 MB、压缩流约 35 MB；后台读取实测得到 110,479 个条目。多个小组件原先各自创建图形上下文并编译相同着色器，也推迟启动期间事件处理。

修复前受控 GPU 启动记录中，画布在 352 ms 显示，分区材质到 1064 ms 才准备好；这直接证明先显示再换材质的问题。这项简化场景未完整复现用户登录时的五秒延迟，不把单一因素认定为全部原因。

修复后在本机真实 GPU、独立 D-Bus/XDG 配置中使用当前壁纸、分区几何、四个自动小组件和只读引用的现有大索引，取得以下单次记录：

| 阶段 | 从构造开始计时 |
| --- | ---: |
| 壁纸解码完成 | 226 ms |
| 分区后台材质完成 | 440 ms |
| 分区表面实际缓存完成 | 877 ms |
| 四个小组件构造完成 | 964 ms |
| 画布显示 | 999 ms |
| 智能空间构造完成 | 1609 ms |

该次启动只出现一次小组件 GPU 初始化，耗时 407 ms。随后索引读取在后台用时 1084 ms，显示卡片及恢复监听用时 392 ms。后者仍是 GUI 线程工作，说明后台加载不等于结果发布完全无成本。以上为受控单次观测，不能保证所有机器或冷登录都在一秒内完成。

计时通过可选环境变量 `UKUI_FENCES_STARTUP_TRACE=1` 开启，只记录阶段、耗时、条目数和 GPU 成功状态，不记录密钥、文件内容或索引条目。

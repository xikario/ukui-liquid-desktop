# 视频壁纸温度/风扇对照与三帧预览（2026-10-04）

## 最终决策与落地方案

采用“原片 60 帧 + 硬件解码 + GPU 输出 + 不可见时暂停”的现有播放方案。当前目标机保留接电最低频率 600000、最高频率 800000 和 simple_ondemand；不将保频扩展自动安装到其他设备。低下限试验已经结束并恢复，测试脚本只作为手动诊断工具。

| 项目 | 固化方案 | 依据及边界 |
| --- | --- | --- |
| 播放质量 | 保持原片分辨率和帧率，硬解失败回到图片 | 不以降帧、转码或软件解码换取表面上的资源下降 |
| 不可见桌面 | 保留完整遮挡、隐藏、锁屏时暂停，恢复可见后继续 | 避免无可见收益的持续播放 |
| 玻璃背景 | 保留首帧缓存 | 不逐帧重建 Qt 背景材质 |
| 频率策略 | 本机保留 600000 下限 | 两种下限的视频实际均升到 800000，未见明确热收益；历史桌面交互曾受益于保频 |
| 视频预览 | 三张关键帧，单线程、异步、去抖、超时、同文件复用，完成即停止 | 真实 4K 视频单张约 0.35 秒；不启动第二个持续播放器 |
| 应用与显示 | 静态/视频统一应用，低清提示可取消，显示模式切换恢复桌面层 | 文件选择不会即时生效或造成虚假未保存提示 |

验收结论：功能可以固化并交付，持续播放功耗“接近静态或最多高 5%”尚未达成可证明的结果。原策略下，本轮视频比静态 ACPI 温度约高 3.6°C、风扇约高 142 rpm；桌面组 CPU 增加约 4.44 个整机百分点，但整机总 CPU 增加约 8.38 个百分点且存在其他后台活动。需要最低发热时使用已有静态类型；需要动画时保留 60 帧，由用户明确选择，不自动替换为静态。

本轮不再调整 GPU 最高频率、合成器或驱动参数。若以后继续优化持续播放功耗，先使用同一片源、相同后台状态和足够长的热稳定阶段测量整机瓦数/呈现帧时间，再逐项验证渲染路径改动；未取得收益前不纳入默认配置。

## 视频设置预览

视频草稿现在按需读取片长，在约 10%、50%、90% 三个目标位置附近生成带时间标记的关键帧缩略图；时间标注为“秒附近”。关键帧间隔很长的片源可能显示重复画面。预览不会切换当前壁纸、保存草稿、启动持续播放或更改视频帧率；点击“应用”才走既有验证/低分辨率确认和保存流程。

`VideoWallpaperPreview` 使用独立异步 QProcess，250 ms 合并路径输入；每次最多一个进程，ffprobe 和每帧 FFmpeg 各有 5 秒期限。FFmpeg 输出最多 320×180 图像，解码/滤镜/输出均限制单线程。提取三帧后停止工作。换文件会终止旧进程并丢弃旧结果；切回静态和关闭设置也会取消。已完成的同一文件按路径、大小和修改时间复用预览，不因状态更新反复提取。

9 项相关 CTest 全部通过。除原有保存/显示切换回归外，新增三帧有实际像素、草稿预览不启动壁纸、快速路径变化不保留旧结果、真实 FFmpeg 视频的首尾缩略图不同、取消清空预览等验证。

部署过程中补充了真实 4K 视频验证：精确 seek 单帧需要 5.20 秒，超过 5 秒期限；仅关闭精确 seek 仍会因时间戳同步解码丢帧，耗时 10.68 秒。改为 `-noaccurate_seek -vsync 0` 后，三个位置单帧分别为 0.341 / 0.351 / 0.344 秒，保留单线程和 5 秒上限。实际播放参数不变。

## 当前机器与对照边界

早期两轮测试保持太空舱原片 3840×2160 / 60 fps。当前 FTG340 governor 为 simple_ondemand，最低频率 600000、最高 800000；保频服务启用，首次安装保存的 OEM 最低值为 200000。频率数值沿用驱动节点单位。

采样温度是 ACPI thermal zone，不是经过确认的 GPU 核心温度；风扇取 acpi_fan 转速。没有整机瓦数或声压级测量。CPU 汇总包含 Fences、播放器、Xorg、KWin 和驱动线程，并以 8 核整机能力归一化。记录播放状态，避免把暂停混入有效播放性能结论。

第一轮按视频 120 秒、静态 180 秒、视频 180 秒执行。但其他桌面活动并不相同，部分视频阶段发生遮挡暂停。静态期间曾观察到两个 Chrome 进程合计约 1.3 核 CPU，显卡仍进入最高频率档。因此不能将静态与视频的温差直接归因于壁纸，也不能据此声称视频更节能。

各阶段最后 60 秒的读数如下。不是隔离后的壁纸独占功耗对比，GPU 档位列为最高档出现的每秒采样数：

| 阶段 | 平均 ACPI 温度 | 平均风扇 | 整机总 CPU | 800000 档采样 |
| --- | ---: | ---: | ---: | ---: |
| 第一轮视频 A（末分钟含暂停） | 49.8°C | 3186 rpm | 18.4% | 56/60 |
| 第一轮静态 | 48.6°C | 3167 rpm | 17.9% | 25/60 |
| 第一轮视频 B（末分钟含暂停） | 46.7°C | 3044 rpm | 5.6% | 0/60 |
| 第二轮静态 | 49.7°C | 3183 rpm | 27.7% | 41/60 |
| 第二轮视频 | 47.0°C | 3183 rpm | 7.1% | 0/60 |

第二轮尝试显示桌面以减少前台干扰，但用户活动与后台浏览器负载仍然变化，故仍不能视为控制变量实验。视频 B 在末分钟全程播放、实际频率 600000、原片/估算解码 60 fps、报告丢帧 0；静态末分钟总 CPU 高达约 27.7%。不能将静态较热理解成视频更节能。

短时间温度从 50°C 降到 47°C 时，风扇仍约 3183 rpm，显示出散热控制滞后/阈值的影响；只有一个 ACPI 温度读数，无法区分具体控制因素。当前数据无法量化单独视频造成的风扇增量。采样期间没有编译或运行测试程序，源代码编辑不改变运行中的二进制。


## 首轮后制定的保频试验

600000 是频率下限，并非锁死频率；负载高时仍升至 800000。它会阻止空闲时回到 200000/400000，可能提高空闲功耗。静态阶段也出现最高频率，说明其他桌面活动同样会影响显卡与风扇。

下一项有意义的实验是保持视频 60 fps、供电/后台负载一致，临时将下限恢复为 OEM 的 200000，让 governor 自行升频，比较静态与视频的温度、转速、实际频率和丢帧。不能只凭“下限降低”宣称风扇一定安静。

首轮结束时 sudo 要求管理员密码；非交互式停止保频服务的尝试超时，随后确认服务仍 active、下限仍 600000。当时没有更改持久保频配置，也尚未完成低下限的实机 A/B；后续完成情况见下节。准备了 `extras/ukui-desktop-performance/trial-frequency-floor.py`，需用户在本机终端认证；8 分钟测试后恢复原下限。正常中断恢复、并发电源策略变更不被覆盖的隔离测试通过。

随后完成了下面的实机对照，最终决定保留原策略，依据见文首和下表。

证据保存在 Git 忽略目录 `apps/ukui-fences/build/artifacts/video-thermal-preview-20261004/`，含原始逐秒数据、汇总、测试日志、实机预览截图和部署校验。私人截图/用户视频不纳入 Git。


## 浏览器关闭后的低下限实机对照

用户在终端完成认证，脚本将下限从 600000 临时改成 200000，480 秒后实际自动恢复 600000。采样顺序为 200000 静态、200000 视频、自动恢复后 600000 视频、600000 静态；每段 180 秒。两个视频阶段使用同一播放器 PID 27024，没有在恢复下限时重启播放器。采样时未编译、安装或运行测试。

本轮开始时用户已将保存片源换成 `【哲风壁纸】像素风格-光影-冒险.mp4`（3840×2160，60 fps），两种下限使用同一片源，不与上一轮太空舱片源混算。下表取各段末 60 秒：

| 下限 / 模式 | ACPI 温度 | 风扇 rpm | 实际 GPU 档位采样 | 桌面组 CPU / 整机总 CPU |
| --- | ---: | ---: | --- | ---: |
| 200000 / 静态 | 45.67°C | 3041 | 200000×1、400000×31、600000×4、800000×24 | 1.13% / 8.06% |
| 200000 / 视频 | 49.10°C | 3137 | 800000×60 | 5.84% / 16.44% |
| 600000 / 视频 | 49.13°C | 3184 | 800000×60 | 5.61% / 17.05% |
| 600000 / 静态 | 45.53°C | 3042 | 600000×60 | 1.17% / 8.67% |

视频末分钟全程 playing，VAAPI 解码，sourceFps / decodedFps 为 60。200000 阶段首次启动所在循环观测到 5 帧丢帧，后续采样到的循环计数均为 0；600000 阶段未观测到新增丢帧。mpv 的 frame-drop-count 会在循环时归零，因此按 PID/循环保存采样最大值，不能只看最终 0 就声称整个测试零丢帧；1 秒外部采样和播放器状态更新仍可能漏掉循环尾部事件，也不是逐帧呈现测量。

保留 600000 策略时，视频相对静态的桌面进程组约增加 4.44 个整机 CPU 百分点，温度约高 3.6°C、风扇约高 142 rpm。桌面组包含共享 Xorg/KWin，不能视为视频独占的 CPU 增量；整机总 CPU 增量约 8.38 个百分点，不能宣称整机增量已低于 5%。静态时的独立 3 秒进程快照发现 ChatGPT 相关进程约 4.47% 整机 CPU，其他后台仍存在。

结论：两种下限的视频实际频率都持续升到 800000，温度几乎相同；较低下限的视频风扇末段也升至约 3183 rpm，末分钟均值较低包含风扇升速滞后，不能解释为稳定降噪收益。两个静态段温度/风扇也很接近。当前证据不支持为这部视频永久取消保频；保留原 600000 配置，不改变帧率、分辨率或最高频率。较低下限能让静态进入更低档，但在本次负载和采样长度下没有明确热收益。长时间稳定温度、声音大小和整机功耗仍需更长时间及相应测量手段。

当前已经使用原片硬解、GPU 输出、遮挡暂停和静态玻璃缓存。此次新增优化是按需关键帧预览，停止提取后无持续播放负载；不声称它降低了壁纸持续播放功耗。
